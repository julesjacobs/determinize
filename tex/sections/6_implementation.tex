\section{Implementation}
\label{sec:implementation}

Every theorem of the previous sections is mechanized in the Lean programming language~\cite{lean}, using Mathlib's formalization of measure theory and probability~\cite{mathlib}, in particular the Giry monad, Markov kernels and their disintegration, as well as the standard continuous and discrete distributions. The complete compilation, verification and execution pipeline is outlined in \cref{fig:architecture}.

\input{figures/architecture}

First, the source program is parsed and desugared; this step is unverified. Type inference then fills in every omitted $\E/\G$ annotation and returns a typed program $e_{\mathrm{src}}$. By \cref{thm:inference}, it returns the greatest completion, which has an $\E$ at every site where some completion has one. The determinization function of \cref{def:determinization} then replaces every $\E$-mode sample by a mean site, marked $\M$, and returns a well-typed program $e_{\mathrm{det}}$.

The soundness theorems (\cref{thm:trace-soundness,thm:expectation,thm:variance,thm:convex-function}) relate $e_{\mathrm{src}}$ and $e_{\mathrm{det}}$ through the measure-theoretic semantics of \cref{fig:semantics}, which we define in Lean with the Giry monad. To draw samples, an unverified interpreter runs either program with floating-point numbers and pseudo-random samplers. The theorems do not cover it, and it cannot be proved to agree with the semantics: floating-point numbers are not real numbers, so its results only approximate those of the semantics.

If a program has finitely many reachable states and draws only from Bernoulli and discrete distributions, its output law is that of a finite Markov chain, and its return probability and first and second moments solve linear equations over that chain. The tool builds the chain by exploring the machine states of the program and merging equal ones. Numbers added to the result of a pending call become rewards on transitions, so that loops that accumulate a sum stay finite. A solver verified in Lean, or alternatively Storm~\cite{hensel2022storm}, solves the equations exactly. Both write a certificate that Lean's kernel checks, which proves that the explored program is domain-safe, that its output law is that of the chain, and that the numbers are its exact return probability and first and second moments. From these, the tool reports the probability that the program returns, and the mean and variance of the result given that it returns. If the explored program is $e_{\mathrm{det}}$ and $e_{\mathrm{src}}$ is domain-safe with a defined expectation, \cref{thm:expectation} guarantees that $e_{\mathrm{src}}$ has the same mean.

Most of the Lean development, including the definitions and theorem statements, was written by large language models (Claude Fable 5.1, Claude Opus 5.5 and GPT 6 Astra). Since Lean's kernel checks the proofs but not whether a statement says what this paper says, we separated the code into two parts:

\begin{enumerate}
\item \textbf{Specification}: the definitions in \texttt{Spec/}, such as the syntax, typing rules, semantics and determinization, and the full statement of every theorem in \texttt{Theorems.lean}, about 1,600 lines in total. We reviewed both line by line against \cref{sec:language,sec:type-system,sec:soundness}, and reviewed every later change to them.
\item \textbf{Proofs and procedures}: about 26,000 lines in \texttt{Proof/} that prove the statements, and the executable code that some statements are about, such as type inference. \texttt{Theorems.lean} proves each theorem by a single reference to this part. Its last command fails the build if a theorem uses an axiom other than \texttt{propext}, \texttt{Classical.choice} and \texttt{Quot.sound}, or if its statement depends, through anything other than proofs, on a declaration in \texttt{Proof/}.
\end{enumerate}

To trust the tool's results, one has to rely on Lean's kernel, these three axioms, the specification and the Mathlib definitions it uses, and the Lean compiler for the output of type inference. Exact results come with a certificate that the kernel checks against the specification. The parser and the floating-point interpreter are unverified.

To show interactively how determinization works, we also provide a browser-based simulator, an unverified TypeScript port of the tool's parser, type inference, determinization, interpreter and finite graph construction. Its editor shows the $\E/\G$ annotations that type inference fills in, next to the determinized program. It steps through a run of the source program, the symbolic state of \cref{sec:proof} and the determinized program side by side, sharing their $\G$ draws. It also runs both programs many times and shows their empirical output distributions, means and variances, next to their exact values where the graph is finite. Its tests compare it with the Lean tool on every program of our test corpus.
