\section{Implementation}
\label{sec:implementation}

Every theorem of the previous sections is mechanized in the Lean programming language~\cite{lean}, alongside an execution pipeline of which only the parser, the floating-point interpreter and the external Storm solver are unverified. The formalization relies on Mathlib's formalization of measure theory and probability~\cite{mathlib}, in particular the Giry monad, Markov kernels and their disintegration, as well as the standard continuous and discrete distributions. The final implementation was mostly carried out by a combination of Claude Fable 5.1, Claude Opus 5.5 and GPT 6 Astra. In order to make it clear which parts of the pipeline need human review and which ones can be left to the Lean kernel, we separated the code into two parts:

\begin{enumerate}
\item \textbf{Trusted surface/specifications}: This part requires the most scrutiny. It contains the language's syntax, the typing rules, the semantics, the determinization as well as the theorem statements. Additionally, it contains the non-verified functions like the parser or floating-point interpreter.
\item \textbf{Lean-checked proofs and procedures}: This part contains the actual proofs of the theorems stated in the trusted surface, as well as the parts of the pipeline whose correctness is guaranteed by definitions and theorems inside the trusted surface. It is a current limitation of the Lean programming platform that there is no compiler guarantee that all theorems have accompanying proofs, therefore requiring a manual check.
\end{enumerate}

The complete compilation, verification and execution pipeline is outlined in \cref{fig:architecture}. We will briefly describe the individual steps in the following.

\paragraph{Parse and elaborate} First, the source code is parsed, desugared and variable names are replaced by de~Bruijn indices. This part is unverified and, as such, part of the trusted surface.

\paragraph{Infer types and $\E/\G$} Afterwards, the types of the program are inferred and all sampling sites are annotated with either $\E$ or $\G$. The code is verified to produce a correct typing as well as mode annotation, and the program is furthermore shown to assign as many $\E$-sites as possible. At the end of this step, the user has a well-typed program $e_{\mathrm{src}}$.

\paragraph{Determinize} The determinization function of \cref{def:determinization} walks through the syntax tree and replaces every $\E$-mode sample by a mean site, marked $\M$. The pipeline runs the same Lean definition that the soundness theorems are stated about, with rational instead of real literals. The output is a well-typed, determinized program $e_{\mathrm{det}}$.

\paragraph{Soundness theorems} Suppose $\vdash e_{\mathrm{src}}:\tyR\E$ and $e_{\mathrm{src}}$ is domain-safe. The formalized soundness theorems then show that $e_{\mathrm{det}}$ has the same expectation as $e_{\mathrm{src}}$ whenever the latter is defined (\cref{thm:expectation}), that its variance is no larger whenever $e_{\mathrm{src}}$ returns with positive probability and has a finite second moment (\cref{thm:variance}), and that, for almost every $\G$ trace, $e_{\mathrm{det}}$ returns the conditional mean of $e_{\mathrm{src}}$ (\cref{thm:trace-soundness}).

\paragraph{Measure-theoretic semantics} In order to prove exact statements like the soundness theorems, we provide an implementation of the small and big step semantics based on the Giry-monad. Due to the non-computable nature of exact reals, these semantics can not be used to compute actual results.

\paragraph{Floating-point interpreter} In order to be able to run the program and to carry out actual sampling, we also provide corresponding non-exact floating-point semantics. This part is unverified since floating point arithmetic is inherently imprecise.

\paragraph{Finite graph construction} In case the program's state space is finite, we can actually compute exact results using the theory of finite Markov chain. In this case, the program computes the finite state graph and allows one to continue with it in two ways:

\paragraph{Exact rational solver} The above graph can be used to directly compute the exact mean and variance by our own verified matrix solver.

\paragraph{Storm solver} Alternatively, the finite state graph can be passed to the external probabilistic model checker Storm~\cite{hensel2022storm}.

\paragraph{Certificate checker} The certificate that Storm produces is checked and it is verified that any such certificate corresponds to the correct expected value for the input program.
