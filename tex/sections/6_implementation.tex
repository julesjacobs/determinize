\section{Implementation}
\label{sec:implementation}

The theory from the previous sections is completely formalized and accompanied by a complete execution pipeline in the Lean programming language \cite{lean} with the formalization relying heavily on previous formalizations in the Mathlib library \cite{mathlib}. The final implementation was mostly carried out by a combination of Claude Fable 5.1 and ChatGPT Astra. In order to make it clear which parts of the pipeline need human review and which ones can be left to the Lean type-checker, we separated the code into three parts:

\paragraph{Trusted surface} This part requires the most scrutiny. It contains the language's syntax, the typing rules, the semantics, the determinization as well as the theorem statements.

\paragraph{Mechanized proofs} This part contains the actual proofs of the theorems stated in the trusted surface. It does not require human review since the correctness is guaranteed by the Lean type checker.

\paragraph{Execution pipeline} This part contains the entire non-verified pipeline, i.e. parsing, type inference, finite graph construction, etc. These steps produce certificates whose correctness is verified by [TODO: what?]

\paragraph{Parsing, elaborate, infer types and E/G.} First, the source code is parsed and typed, including the sampling modes $\E$ and $\G$ [TODO: check whether $\M$ is already mentioned in the article before this]. Due to the complexity of the typing algorithm, the formalization of this step is out of scope of this article.

\paragraph{Typing and annotation checker} Even though the previous typing step is not itself formalized, verifying the correctness of the typing is straightforward and its own correctness verified as well. At the end of this step, the user has a well-typed program $e_{\mathrm{src}}$.

\paragraph{Determinize} This is the determinization function. It is trivial and simply walks through the syntax tree, transforming every $\E$-mode sample into a sample at mode $\M$. The output is a well-typed, determinized program $e_{\mathrm{det}}$.

Once we have a well-typed program $e$, we can evaluate it. For this, we offer multiple options:

\paragraph{Measure-theoretic semantics} We can reason about its exact semantics and in particular its output measure $\mu_e$. The soundness theorems guarantee that the exact output measures $\mu_{e_{\mathrm{src}}}$ and $\mu_{e_{\mathrm{det}}}$ agree in a meaningful way (cf.\ Sections \ref{sec:soundness} and \ref{sec:proof}).

\paragraph{Floating-point interpreter} The above semantics rely on exact reals which are not computable in a meaningful way. In order to be able to run the program and to carry out actual sampling, we also provide corresponding non-exact floating-point semantics.

\paragraph{Finite graph construction} In case the program corresponds to a Markov chain with only finitely many states, we can create its state graph and continue with it in two ways:

\paragraph{Exact rational solver} The above graph can be used to directly compute the exact mean and variance by our own verified matrix solver.

\paragraph{Storm solver} Or alternatively the finite state graph can be entered into the external Storm solver [TODO: cite].

\paragraph{Certificate checker} Our verified certificate checker verifies that the results from our own solver are the same as from the storm solver.
